# บทเรียนจากข้อผิดพลาด (อ่านก่อนเริ่มงานทุกครั้ง)

Friend สั่งไว้ (2026-11-08): "จดข้อผิดพลาดทุกอย่างไว้เป็นบทเรียน เพื่อป้องกันไม่ให้เกิดขึ้นอีกในอนาคต"

ทุกข้อเขียนแบบเดียวกัน: **พลาดอะไร** → **ต้นเหตุ** → **กฎกันพลาด** ถ้าพลาดเรื่องใหม่ ให้เพิ่มเข้าไฟล์นี้ในแชทเดียวกันทันที ไม่ต้องรอให้ Friend สั่ง

---

## ตรวจก่อนส่งงานให้ Friend ทุกครั้ง (ย่อจากบทเรียนด้านล่าง)

1. เทียบกับคลิปตัวอย่างของ Friend แบบวางข้างกัน ไม่ใช้สายตาตัวเองเป็นมาตรฐาน (ข้อ 7)
2. เปลี่ยนประโยคแล้วร่างยังใช้ได้ไหม ของในภาพมาจากใบประกอบทั้งหมดไหม (ข้อ 8)
3. ดูภาพทีละเฟรม ห่างกัน 0.1–0.2 วินาที รอบทุกจังหวะสำคัญ ครบ 6 สไตล์ ไม่ใช่ดูแค่ภาพปก (ข้อ 9)
4. ไล่กฎ 5 ข้อของร่าง (DECISIONS หัวข้อกฎการจัดวางและจังหวะของร่าง): ของที่เชื่อมสองสิ่งอยู่บนแนวตรง · เอฟเฟกต์ขึ้นหลังของมาถึง · เครื่องหมายอยู่กลางช่องว่าง · คำกึ่งกลางใต้ไอคอนและอยู่บรรทัดเดียวกัน · คลื่นทรงเดียวกับชิ้นและอยู่ด้านหลัง
5. รัน `check_overlap.js` ทั้ง 6 สไตล์ และ `node test_picker.js`
6. แก้ชิ้นส่วนที่ใช้ร่วมกัน → หาให้ครบว่าร่างไหนใช้ แล้วทำคลิปใหม่ทั้งหมดและบอก Friend (ข้อ 10)
7. งานเบื้องหลัง: ดู log ภายใน 1 นาทีหลังสั่ง (ข้อ 11)
8. ก่อนบอกว่า "บันทึกแล้ว": ตรวจว่า `HEAD` ตรงกับ `origin` (ข้อ 22)

## ก. การคุยกับ Friend

**1. อธิบายจน Friend "งง" (3 ครั้งในแชท `ccr-d0ede324-wsetx8`)**
- พลาด: ตอบเรื่อง 1,000 ชิ้น × 100 สไตล์ยาวเกินไป · บอก "โครงเรื่อง 10 แบบ (แยกย่อยได้ 21 แบบ) มีแล้ว 10 จากเป้า 25–30" · อธิบายแผนจน Friend ถามว่า "สรุปคือตอนนี้เราจะทำยังไงนะ ผมเริ่มงง"
- ต้นเหตุ: ใช้ศัพท์ข้างในระบบ (โครงเรื่อง สูตร ชิ้นส่วน ท่า) มีตัวเลขหลายตัวซ้อนกันในประโยคเดียว และเล่าหลายเรื่องพร้อมกัน
- กฎ: ใช้แค่คำที่ตกลงกับ Friend แล้ว (**หมวด ร่าง ร่างเล็ก ใบประกอบ**) · ประโยคละไม่เกิน 1 ตัวเลข · ตอบเรื่องที่ถามก่อนแล้วจบ · อธิบายด้วยตัวอย่างจริง 1 ตัว ไม่เปรียบเทียบกับเรื่องอื่น (Friend: "ไม่ต้องเปรียบเทียบกับเรื่องอื่น") · ถ้าอธิบายด้วยภาพได้ ใช้ภาพ

**2. บอกตัวเลขที่ยังไม่ได้นับ หรือคำยืนยันที่ยังไม่ได้ลอง**
- พลาด: "1,000 บทน่าจะใช้ของซ้ำกันแค่ราว 200 อย่าง" (Friend: "แล้วทำไมน่าจะใช้ของซ้ำกันแค่ราว 200 อย่าง") · "ร่างแยกแทบไม่มีต้นทุน" (ผิด: ร่างแต่ละร่างต้องเขียนเองจริง) · "overlay ใช้ร่างเดิมได้ ไม่ต้องวาดใหม่" (ผิด: Friend "ยังไม่ชอบ" ต้องทำร่างเล็กทุกร่าง) · บอกว่ามี 14 หมวดโดยไม่บอกว่าครอบคลุมแค่ไหน (Friend: "ทำไมถึงมี 14 หมวด แล้วมันครอบคลุมหรือยัง")
- ต้นเหตุ: ตอบจากความรู้สึก แล้วพูดเหมือนเป็นข้อเท็จจริง
- กฎ: ตัวเลขที่บอก Friend ต้องนับหรือวัดแล้ว ถ้ายังไม่ได้นับ ให้พูดว่า "ผมกะไว้" และบอกว่ากะจากอะไร · บอกเหตุผลคู่กับตัวเลขทุกครั้ง · ห้ามบอกว่า "ไม่ต้องทำเพิ่ม" หรือ "ไม่มีต้นทุน" จนกว่าจะลองให้เห็นผลจริง

**3. เข้าใจคำของ Friend ผิด แล้วลงมือทำเลย**
- พลาด: คิดว่า "ร่างแยก" คือตาชั่งหลายแบบ Friend ต้องแก้ว่า "ไม่ใช่สิ ร่างแยกไม่ได้หมายถึงตาชั่งหลายแบบ แต่หมายถึง motion graphics หน้าตาแบบไหนก็ได้ที่สื่อความหมายเดียวกัน"
- ต้นเหตุ: ตีความคำใหม่เอง ไม่ได้ทวนให้ Friend ยืนยันก่อน
- กฎ: คำใหม่หรือไอเดียใหม่จาก Friend ให้ทวนความเข้าใจ 1 ประโยค + ตัวอย่าง 1 อย่าง แล้วรอ Friend ตอบก่อนเริ่มงาน

**4. ลืมข้อตกลงที่ Friend ตัดสินไว้แล้ว**
- พลาด: คุยเรื่องคู่มือที่ AI ต้องอ่านแล้วแพงขึ้น โดยไม่พูดถึงข้อตกลงลดไอคอนเหลือราว 300 เพื่อลดต้นทุน Friend ต้องเตือนเอง ("ไอคอนเราลดเหลือ 300 ไม่ใช่หรอ เหมือนว่าผมเคยตัดสินใจนะ")
- กฎ: ก่อนตอบเรื่องต้นทุน ตัวเลข หรือแผน ให้ค้นใน `DECISIONS.md` ก่อนทุกครั้ง แล้วอ้างข้อตกลงที่เกี่ยวข้อง

**5. เสนองานใหม่โดยไม่พูดถึงงานที่ค้างอยู่**
- พลาด: เสนอเริ่มรอบที่ 2 (หมวดใหม่) ทั้งที่หมวดของรอบที่ 1 ยังมีแค่ร่างเดียว Friend ต้องถาม "ไม่ต้องกลับไปของรอบแรกก่อนหรอ"
- กฎ: ทุกครั้งที่เสนองานถัดไป ให้ไล่ก่อนว่ามีอะไรที่ Friend สั่งแล้วยังไม่เสร็จ แล้วใส่ไว้ในข้อเสนอด้วย

**6. ข้อเสนอที่ต้องถอนทีหลัง**
- พลาด: เสนอ "ใช้ชิ้นร่วมกันแล้วเปลี่ยนแค่ชุดเครื่องมือ" และ "แต่ละสไตล์วาดบทใหม่ทั้งหมด" แล้วต้องถอน (Friend ถามว่า 1,000 ชิ้น × 100 สไตล์ = 100,000 ชิ้นหรือ)
- ต้นเหตุ: ไม่ได้คิดต่อว่าข้อเสนอจะเป็นอย่างไรเมื่อถึงเป้าจริงของ Friend (สไตล์หลายร้อยแบบ ต้นทุนต่อคลิปเท่าเดิม)
- กฎ: ก่อนเสนอวิธีใหม่ ให้คิดผลที่ขนาดเป้าหมายจริง (หลายร้อยสไตล์ หมวดละ 20 ร่าง) ถ้ายังไม่แน่ใจ ให้ทดสอบเล็ก ๆ ก่อนแล้วค่อยเสนอ

## ข. คุณภาพงาน (มาตรฐานคือคลิปตัวอย่างของ Friend)

**7. overlay รอบแรก Friend "ยังไม่ชอบ"**
- พลาด: ย่อภาพเต็มจอไปวางเหนือหัว มีประโยคในการ์ด ของเล็ก
- ต้นเหตุ: ตัดสินด้วยสายตาตัวเอง ไม่ได้เทียบกับคลิป overlay ของ Friend ข้างกันก่อนส่ง
- กฎ: งานภาพทุกชิ้นต้องเทียบกับคลิปตัวอย่างของ Friend ข้างกันก่อนส่ง แล้วถามตัวเองว่า "คลิปของ Friend ทำแบบนี้ไหม" กฎที่ได้จากการเทียบอยู่ใน `library/uni-test/README.md` หัวข้อรอบสิบเอ็ด

**8. ทำร่างเล็กจากบทพูดของ Friend ซึ่งไม่ใช่เลโก้**
- พลาด: Friend ชอบ แต่ "ไม่เอาไปใช้จริง เพราะมาจากบทพูดของผม ที่เราต้องการจริง ๆ คือเลโก้"
- กฎ: ทุกร่างต้องสร้างจากช่องในใบประกอบเท่านั้น ทดสอบด้วยประโยคทั่วไปที่ไม่ใช่ของ Friend ถ้าเปลี่ยนประโยคแล้วภาพพัง แปลว่ายังไม่ใช่เลโก้

**9. จุดผิดในภาพที่ Friend ต้องจับเอง (ต้องจับได้เองก่อนส่ง)**
| สิ่งที่ Friend เจอ | ต้นเหตุ | กฎกันพลาด |
|---|---|---|
| โดมิโนไม่ลื่น | แต่ละตัวล้มแยกกัน ไม่ได้ล้มต่อเนื่องจากการผลักครั้งเดียว | ท่าที่เป็นลูกโซ่ต้องคำนวณจากจุดชนจริง (`R1.topple`) |
| การ์ดกระจกทับกัน "ตรวจดูและแก้ไขทุกการ์ด" | ไม่มีตัวตรวจ ดูด้วยตาแล้วพลาด | รัน `check_overlap.js` ทุกร่างใหม่ ครบทุกสไตล์ |
| แบ่งจอ จังหวะที่คนพูดย่อลงกรอบล่าง | กรอบไม่วิ่งตามขอบวิดีโอ หน้าต่างกับซับขึ้นระหว่างที่ยังย่ออยู่ | ของใหม่ขึ้นหลังการย่อเสร็จ และหายก่อนขยายกลับ |
| "ไอคอนมันต้องตรงกับจุดสิ" | วางจุดความคิดด้วยตัวเลขที่กะด้วยตา | ของที่เชื่อมสองสิ่งให้คำนวณจากตำแหน่งของสองสิ่งนั้น |
| "วงกลมขึ้นมาก่อนที่ไอคอนจะเลื่อนขึ้นไปได้ไง" | ตั้งเวลาเอฟเฟกต์ตามคำสำคัญ (`T.hit`) ไม่ใช่ตามเวลาที่ของมาถึงจริง | คำนวณเวลาที่ของมาถึงจากความยาวท่า แล้วเริ่มเอฟเฟกต์หลังจากนั้น |
| "เครื่องหมายเท่ากับไม่อยู่กึ่งกลาง และตัวอักษรไม่อยู่กึ่งกลางไอคอน" | `kit.label` จัดกลางด้วย `transform` แล้วท่าเข้าเขียนทับ ทั้งที่ README เขียนไว้แล้วว่า "ห้ามวางตำแหน่งด้วย transform" | เขียนกฎแล้วต้องค้นโค้ดด้วยว่าไม่มีที่ไหนผิดกฎ (`grep "translate(-50%"` ต้องไม่เจอ) · ชิ้นใหม่ใน kit ต้องวัดตำแหน่งจริงในภาพ |
| "Effect วงกลมมันแปลก ๆ" (การ์ดพลิก) | ใช้วงกลมอันเดียวกับทุกรูปทรง วาดทับบนการ์ด เริ่มจากในการ์ด และท่าชื่อ `EASE.out` จริง ๆ คือเริ่มช้าแล้วเร่ง วงจึงค้างบนการ์ด | คลื่นต้องทรงเดียวกับชิ้น อยู่ด้านหลัง ออกจากขอบ (`R1.ripple`) · ก่อนใช้ท่าไหน ดูว่าเส้นโค้งของท่าทำอะไรจริง อย่าเชื่อชื่อ |
- กฎรวม: ก่อนส่ง ดูภาพทีละเฟรม (ห่าง 0.1–0.2 วินาที) รอบทุกจังหวะสำคัญ ครบ 6 สไตล์ ภาพปกภาพเดียวไม่พอ เพราะจุดผิดข้างบนเกือบทั้งหมดเป็นเรื่องจังหวะและการเคลื่อนไหว

**10. แก้ชิ้นที่ใช้ร่วมกัน แล้วกระทบร่างอื่น**
- สิ่งที่เกิด: แก้ `kit.label` แล้วคำในร่างอื่นอีก 11 ร่างเปลี่ยนด้วย (ครั้งนี้เปลี่ยนไปทางดีขึ้น)
- กฎ: แก้ชิ้นใน `kit.js` หรือชิ้นกลาง (`R1` `R2` `R3`) ให้ค้นว่าร่างไหนใช้ ทำคลิปใหม่ทุกคลิปที่โดน และบอก Friend ว่าร่างไหนเปลี่ยนไปบ้าง

## ค. วิธีทำงานและเครื่องมือ

**11. สั่งงานเบื้องหลังจากผิดโฟลเดอร์ แล้วคิดว่ากำลังทำอยู่**
- พลาด: สั่งทำคลิปใหม่ 63 คลิปจากโฟลเดอร์ที่ไม่มี `render_test.sh` งานล้มทันที แต่ไม่ได้ดู log จนได้รับแจ้งว่าจบ เสียเวลาไปราวครึ่งชั่วโมง
- กฎ: งานเบื้องหลังให้สั่งด้วย path เต็ม (`bash /home/user/Friend/cutpack/engine/uni/render_test.sh …`) หรือ `cd` ในคำสั่งเดียวกัน · สั่งแล้วดู log ภายใน 1 นาทีว่าเริ่มทำจริง · ตรวจคลิปที่ได้ทุกคลิปว่าเป็นไฟล์ใหม่และยาวครบ (`ffprobe`)

**12. ลำดับของคลิป (`@index`) ต้องเหมือนเดิมเมื่อทำคลิปใหม่**
- สิ่งที่เกิด: ตอนทำคลิปใหม่ต้องไปค้นในบันทึกแชทว่าแต่ละคลิปเคยใช้ index อะไร (ถ้าผิด สีพื้นของการ์ดจะเปลี่ยน)
- กฎ: ทุกครั้งที่ทำคลิปชุดใหม่ ให้จดรายการ `ฉาก@index` ที่ใช้จริงไว้ใน `library/uni-test/README.md`

**13. ลบโฟลเดอร์ด้วยตัวแปร** (`rm -rf $P`) ถูกระบบความปลอดภัยบล็อก → ใช้ path เต็มที่เขียนตรง ๆ หรือสร้างโฟลเดอร์ใหม่แทนการลบ

**14. publish หน้า artifact ด้วย `edits` พร้อม `files` ไม่ได้** → แก้ไฟล์ก่อน แล้วค่อย publish พร้อม `files` · session ใหม่ต้อง `read` หน้าเดิมก่อน publish ทับ

**15. stop hook ไม่ยอมให้มีไฟล์ค้างระหว่างทำคลิปนาน ๆ** → commit เฉพาะไฟล์ที่เขียนเสร็จแล้ว (ไม่เปลี่ยนนานกว่า 15 วินาที) ไฟล์ที่กำลังเขียนอยู่รอ commit รอบถัดไป

**16. ดาวน์โหลดจาก Google Drive ไม่ได้** (เครือข่ายของเครื่องไม่อนุญาต) Friend ไม่อนุญาตให้เปิดเครือข่ายเพิ่ม → ห้ามขอเปิดอีก ให้ Friend ส่งไฟล์ในแชทแทน

**17. ชื่อซ้ำกันระหว่างไฟล์ฉาก** (`SAY` มีอยู่แล้วใน `base6_more.js`) → ทุกไฟล์ฉากโหลดรวมกัน ก่อนตั้งชื่อใหม่ระดับไฟล์ให้ค้นทั้งโฟลเดอร์ก่อน

**18. สีที่ไม่ได้ลองกับทุกพื้น** (ตัวเลขสีเขียวมะนาวบนการ์ดขาว · ฟองแชตสีเข้มในธีมสว่าง · ป้ายถูกต้องของกระจกกลายเป็นสีเข้ม) → ชิ้นใหม่ต้องดูครบ 6 สไตล์ ทั้งพื้นสว่างและพื้นมืด

**19. ข้อความยาวล้นกรอบ** (ตัวเลขหลายหลัก) → ทุกช่องที่เป็นข้อความต้องย่อขนาดตามความยาว (`R2.fitSize`) และลองกับข้อความที่ยาวที่สุดที่ AI อาจเขียน

**20. ของในภาพบังกันเอง** (ตราประทับทับคำ · ฝากล่องพาดผ่านของที่ลอยขึ้น · ไอคอนติดตามซ้อนแถวไอคอน · การ์ดแจ้งเตือนชนกันระหว่างเลื่อน) → นอกจากภาพนิ่ง ต้องดูทุกเฟรมระหว่างที่ของกำลังเคลื่อน (ข้อ 9)

**21. ตัวตรวจทับกันฟ้องผิด** (ใบเสร็จที่ซ่อนอยู่ในเครื่องพิมพ์ · ขอบทับกันไม่ถึง 6 px) → ตัวตรวจต้องตัดส่วนที่ถูกซ่อนออกก่อน ถ้าตัวตรวจฟ้อง ให้ดูภาพจริงก่อนแก้

**22. บอก Friend ว่า "บันทึกแล้ว" ก่อนตรวจ** (จากแชทก่อน) → push แล้วตรวจว่า `git rev-parse HEAD origin/<สาขา>` ตรงกันก่อนพูดทุกครั้ง

## ง. บทเรียนจากแชทก่อน ๆ

**23. ใช้เงิน API เกินเส้น 4 ดอลลาร์ที่ Friend ตั้ง** (แชท `ccr-ff7bfa83-eld4pq`) เพราะสคริปต์เช็กยอดแค่ก่อนเริ่มแต่ละคลิป → เช็กยอดกรณีแย่สุดก่อนทุกคำขอ (`plan_d.budget_check`) และห้ามเรียก AI โดยไม่ได้รับอนุญาตจาก Friend

**24. `run_clip.py` ที่ไม่เห็นคีย์ API ทำคลิปแบบไม่มี AI แบบเงียบ ๆ** → ตรวจ `runs.jsonl` ว่ามีต้นทุนจริงทุกครั้ง

**25. ดิสก์เต็มแล้วคลิปขาดกลางทางโดยไม่มี error** → ตรวจความยาว MP4 ด้วย `ffprobe` ทุกคลิป ลบเฟรมหลังเรนเดอร์

**26. รูปแบบคำขอ (schema) ถูก API ปฏิเสธทุกครั้งในรอบแรก** → ลองคำขอเล็ก ๆ 1 ครั้งก่อนรันชุดใหญ่

**27. คลิป 14 คลิป "ต่ำกว่ามาตรฐาน" หลังปรับวิธีวางแผนหลายรอบ** → ต้นเหตุจริงคือวิธีสร้างภาพ ไม่ใช่วิธีเลือกชิ้น · ก่อนเริ่มปรับอะไร ให้เทียบกับมาตรฐานของ Friend ก่อนว่าช่องว่างจริงอยู่ตรงไหน

**28. ลองวิดเจ็ตแบบใหม่แล้ว Friend ให้ย้อนกลับทั้งหมด** → การเปลี่ยนหน้าตาที่ Friend ผ่านแล้ว ทำเป็นตัวเลือกทดสอบแยกไว้ก่อน อย่าเปลี่ยนค่าเริ่มต้นจนกว่า Friend จะผ่าน

**29. เอกสารส่งต่องานฉบับแรกมีกฎที่ไม่ได้มาจาก Friend** → ทุกข้อตกลงต้องบอกที่มา (คำพูดของ Friend + วันที่) ถ้าไม่รู้ที่มา ให้ถาม Friend ก่อนใช้

**30. คลิปของ Friend เป็นของส่วนตัว** → ห้าม commit คลิปของ Friend เข้า repo ใส่ได้แค่ในหน้า artifact ส่วนตัว
